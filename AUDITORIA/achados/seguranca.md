## Achados

### [SEG-001] Isolamento multi-tenant 100% em código — sem RLS como rede de segurança (defense-in-depth ausente)
- **Severidade:** P1
- **Status:** Aberto
- **Local:** `prisma/migrations/**` (44 models, nenhum com RLS de tenant); confirmado por `grep -rl "row level security" prisma/migrations` (só `20260430_notification_preferences` com `deny_anon`, fail-closed, numa única tabela) · memória do projeto: "sem RLS no banco — isolamento em código".
- **Evidência:** Nenhuma tabela com `tenantId` (`Student`, `Enrollment`, `Payment`, `Coupon`, `Course`/`TenantCourse`, `Lead`, `Certificate`, `StudentNote`, `ContactMessage`, `CoursePackage`/`TenantPackage`, etc.) tem `ENABLE ROW LEVEL SECURITY` + policy escopada. O único controle de vazamento cross-tenant é o `where: { tenantId }` aplicado manualmente em cada query. RE-VERIFICAÇÃO 2026-06-24: os 294 route handlers HOJE derivam o tenant da sessão (`requireResellerSession`/`requireResellerSeller`/`requireStudentSession`/`requireAdminSession`) e NENHUM lê `tenantId` de body/query (grep negativo). Os handlers novos confirmam o padrão: `painel/revendas` escopa por `referrerTenantId=sellerTenantId` (`route.ts:71,93`), `painel/revendas/[id]/page.tsx:46` usa `findFirst({ where:{ id, referrerTenantId: sellerTenantId } })`, `painel/alunos/[id]/impersonate/route.ts:33` filtra `findFirst({ id, tenantId })`, `painel/pacotes/pmb/[packageId]/route.ts:60` faz upsert por `tenantId_packageId`. `fulfill.ts:158-164` ainda tem a defesa central `Payment.tenantId === Enrollment.tenantId`. Ou seja: o código atual está correto, mas a invariante depende inteiramente de revisão humana a cada novo handler.
- **Impacto:** Um único `findMany`/`findFirst` futuro sem `where: { tenantId }` (ou um `findUnique` por id sem checagem de posse) vaza dados entre revendas — vazamento cross-tenant é P0. Sem RLS não há contenção: o erro vira incidente direto. O risco cresce na ⚠️MIGRAÇÃO p/ Postgres self-hosted (jobs, psql, ferramentas internas acessam o banco fora da app).
- **Correção:** (a) Mitigação imediata e barata: criar um **teste de isolamento de tenant** automatizado que, para cada model com `tenantId`, exercita um handler representativo com sessão do tenant A pedindo recurso do tenant B e exige 403/404/vazio — rodar no CI (pode ser feito sem aprovação). (b) Roadmap RLS: `ENABLE` + `FORCE ROW LEVEL SECURITY` nas tabelas com `tenantId`, com policy casando o tenant via `set_config('app.tenant_id', ...)` por request (Prisma `$executeRaw` de `SET LOCAL` no início de uma transação). DECISÃO ARQUITETURAL — o `corretor` deve PARAR e descrever (b) ao usuário antes de aplicar (muda o modelo de acesso ao banco e exige Supavisor/pgBouncer compatível com `SET LOCAL`).
- **Verificação:** `npm test -- tenant-isolation` (novo) verde; manualmente: logar como revenda A, `GET /api/painel/alunos/<id-da-revenda-B>` → 404; repetir cupons/certificates/financeiro/vendas/revendas/pacotes. Se RLS adotada: `SELECT relname, relrowsecurity, relforcerowsecurity FROM pg_class WHERE relname IN (<tabelas com tenantId>)` deve mostrar `t` em ambas as colunas.

### [SEG-002] CSP usa `script-src 'unsafe-inline' 'unsafe-eval'` — reduz proteção a XSS
- **Severidade:** P2
- **Status:** Aberto
- **Local:** `next.config.ts:32` (`"script-src 'self' 'unsafe-inline' 'unsafe-eval' https://sdk.mercadopago.com ..."`) e `:31` (`style-src 'self' 'unsafe-inline'`).
- **Evidência:** RE-VERIFICAÇÃO 2026-06-24: política inalterada. Permite execução de qualquer `<script>` inline e `eval()`. Não há XSS reflexivo identificado — os `dangerouslySetInnerHTML` em `src/components/shared/tracking-pixels.tsx:29` e `tracking-purchase-event.tsx:33` usam snippets templated com IDs sanitizados por `sanitizeId()` (regex `[^A-Za-z0-9_-]`) + `JSON.stringify` escapado (`<`/`>`/` `/` `) em `src/lib/tracking/snippets.ts:32-44` — seguros; os de `seo/json-ld.tsx`/FAQ schema são `JSON.stringify` de config estática — seguros. Mas `'unsafe-inline'`/`'unsafe-eval'` removem a principal mitigação caso uma XSS surja.
- **Impacto:** Se uma XSS for introduzida (novo `dangerouslySetInnerHTML` com input de usuário, ou lib comprometida no bundle de pixels white-label que se propaga a todas as vitrines), a CSP não conterá o ataque — execução de script arbitrário no contexto da vitrine/painel.
- **Correção:** Migrar para CSP baseada em **nonce**: gerar um nonce por request no `src/proxy.ts`, propagar via header e aplicar aos `<Script>` do next/script + aos snippets de `snippets.ts`; trocar `script-src` para `'self' 'nonce-<n>' https://sdk.mercadopago.com ...` e remover `'unsafe-eval'` (validar se o SDK do Mercado Pago/Payment Brick exige `eval` — se sim, isolar em iframe sandbox). Manter `style-src 'unsafe-inline'` só se Tailwind/shadcn exigir.
- **Verificação:** `curl -sI https://profissionalizamaisbrasil.com.br | grep -i content-security-policy` não contém `'unsafe-inline'`/`'unsafe-eval'` em `script-src`; smoke test do checkout MP (Payment Brick) e do editor de certificado (iframe blob) continuam funcionando.

### [SEG-007] `nodemailer@7.0.13` HIGH (SMTP command injection via CRLF no `name` do transport) — baixa exploitabilidade, mas advisory novo no audit
- **Severidade:** P2
- **Status:** Aberto
- **Local:** `src/lib/email/smtp.ts:68-69` (`nodemailer.createTransport({ host: cfg.host, ... })`); dep direta `nodemailer` + transitiva via `next-auth@5.0.0-beta.31` e `@auth/prisma-adapter`.
- **Evidência:** `npm audit --omit=dev` reporta `nodemailer <=9.0.0 HIGH` — GHSA-vvjj-xcjg-gr5g "SMTP Command Injection via CRLF in Transport name Option (EHLO/HELO)". A versão instalada (7.0.13) é a **mais recente publicada no npm** — não há patch upstream. RE-VERIFICAÇÃO: o vetor exige controlar a opção `name` do transport; em `smtp.ts` o transport é montado só com `host`/`port`/`user`/`password` de **env** (`SMTP_HOST`/`SMTP_USER`/...) e a opção `name` NÃO é setada — não há caminho de input de usuário até o vetor. A auditoria de 2026-06-20 já monitorava `nodemailer`, mas este advisory específico (CRLF no `name`) é novo/agora flagueado como HIGH.
- **Impacto:** Hoje baixíssimo na prática (sem input de usuário no `name` e config SMTP é app-controlled via env). É uma HIGH aberta no inventário de supply-chain sem fix disponível; vira relevante se algum dia o `name`/host do transport passar a derivar de dados de tenant (ex.: SMTP por revenda).
- **Correção:** (a) Monitorar e bumpar `nodemailer` assim que sair versão ≥9.0.1 (cobre o advisory) — automatizável via SEG-005. (b) Garantir que a config do transport (`host`, `name`) nunca derive de input de usuário/tenant. - **Verificação:** após bump, `npm ls nodemailer` → ≥9.0.1 e `npm audit --omit=dev` não lista mais o HIGH; envio de email de teste continua funcionando.
