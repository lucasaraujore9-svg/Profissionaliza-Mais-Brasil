### [DB-001] BI hub (admin) roda agregações platform-wide sobre `created_at`/`paid_at` SEM índice — seq scan nas 3 maiores tabelas a cada carga de aba
- **Severidade:** P1
- **Status:** Aberto
- **Local:** src/lib/reports/aggregations.ts:52-70 (`approvedRevenueByBucket`: `payments WHERE mp_status='APPROVED' AND paid_at >= $2 AND paid_at < $3`, sem tenant → sem índice líder) · :95-118 (`studentCountByBucket`) · src/lib/reports/bi/visao-geral.ts:37-59 (`student.count`/`enrollment.count` por `createdAt` range + `payment.groupBy` por `tenantId` com `paidAt` range) · src/lib/reports/bi/alunos-matriculas.ts:32-51 (5+ `count`/`groupBy` sobre `createdAt`, incl. `student.groupBy by estado`) · src/lib/reports/bi/indicacoes-comissoes.ts:37-63 (`referralCommission`/`referralMonthlyCommission.aggregate` por `createdAt` range) · prisma/schema.prisma (Student sem `@@index([createdAt])`; Enrollment sem `@@index([createdAt])`; Payment só tem `@@index([tenantId, paidAt])`)
- **Evidência:** Índices atuais (verificados no schema): **Student** → `[tenantId]`, `[plataformaAlunoId]`, `[tenantId,status]`, `[resetToken]` (nenhum em `created_at` nem `estado`). **Enrollment** → `[tenantId]`, `[studentId]`, `[status]`, `[tenantId,status]`, … (nenhum em `created_at`). **Payment** → `[tenantId]`, `[tenantId,createdAt]`, `[tenantId,paidAt]` (nenhum índice com `paid_at`/`created_at` como coluna **líder** e sem `mp_status`). O dispatcher `bi/[tab]/route.ts` chama os módulos **sem `tenantId`** (o admin filtra por `segment` pmb/revenda/todos, aggregations.ts:29-38 → `AND tenant_id IS NULL`/`IS NOT NULL`/nada). Sem coluna de tenant específica no filtro, o índice composto `[tenantId, paidAt]` **não é usável** (líder não-restrito) → o Postgres cai em **seq scan** filtrando por range de data. A aba "Visão Geral" sozinha dispara ~6 varreduras (2× `student.count`, 2× `enrollment.count`, `approvedRevenueByBucket`, `payment.groupBy`); "Alunos & Matrículas" outras ~8; ×9 abas de BI. `alunos-matriculas.ts:49-51` ainda faz `student.groupBy({ by: estado })` sobre `created_at` range com `estado` sem índice.
- **Impacto:** Hoje (tabelas pequenas) responde. Conforme `payments`/`enrollments`/`students` crescem, **cada carregamento** de qualquer aba do BI admin faz full scan das maiores tabelas — latência linear no volume, timeouts do `force-dynamic` e pressão de I/O que degrada o app inteiro (mesma pool). É o gargalo previsto na referência §3 ("detectar tabelas com muito seq scan"). Painel (tenant-scoped) sofre menos porque o `[tenantId]` líder restringe antes do filtro de data — mas ainda filtra `createdAt` sem índice dentro do tenant.
- **Correção:** Adicionar índices via migration idempotente nova (`prisma/migrations/20260703_bi_date_indexes/migration.sql`, `CREATE INDEX IF NOT EXISTS`) e declarar os `@@index` correspondentes no `schema.prisma`:
  1. `Student`: `@@index([createdAt])` (e opcional `@@index([estado])` para o groupBy geográfico).
  2. `Enrollment`: `@@index([createdAt])` e `@@index([status, createdAt])`.
  3. `Payment`: `@@index([paidAt])` (platform-wide por data) **ou**, melhor, índice parcial `CREATE INDEX payments_approved_paid_at_idx ON payments (paid_at) WHERE mp_status='APPROVED'` (cobre exatamente o filtro de `approvedRevenueByBucket`/`payment.groupBy`).
  4. `ReferralCommission`/`ReferralMonthlyCommission`: `@@index([createdAt])` (aggregate por range).
  ⚠️ Como o runner (`apply-pending-migrations.mjs`) envolve cada arquivo numa transação, **não** use `CONCURRENTLY` (ver DB-007) — o `CREATE INDEX` simples pega `SHARE lock` e **bloqueia escritas** nessas tabelas durante o build. Em prod cheia, aplicar em janela de baixo tráfego, ou (melhor) rodar os índices grandes manualmente com `CREATE INDEX CONCURRENTLY` fora do runner e apenas registrar o filename no tracking. **⚠️MIGRAÇÃO VPS:** no Postgres self-hosted o mesmo se aplica; aproveitar o cutover para criar já com CONCURRENTLY.
- **Verificação:** `EXPLAIN (ANALYZE, BUFFERS)` de `SELECT date_trunc('day',paid_at), sum(amount) FROM payments WHERE mp_status='APPROVED' AND paid_at >= now()-interval '30 days' GROUP BY 1` mostra **Index Scan** (não Seq Scan). `select relname, seq_scan, idx_scan from pg_stat_user_tables where relname in ('payments','enrollments','students');` — `idx_scan` cresce e `seq_scan` estabiliza após deploy. `npx prisma validate` OK.

### [DB-002] Bucket `certificates` guarda PII (CPF + nome no PDF) — código já não persiste URL pública, mas privacidade do bucket + backfill de linhas legadas continuam pendentes de verificação manual
- **Severidade:** P1 (era P0 — rebaixado; **volta a P0 se o bucket estiver público em prod**)
- **Status:** Aberto (mitigado no código; exige verificação no Supabase + backfill)
- **Local:** src/lib/certificates/generate-pdf.ts:175-184 (`path = pdfPathFor(cert.tenantId, cert.id)` → grava `pdfUrl: upload.path` — **o PATH, não a URL pública**) · src/lib/certificates/storage.ts:79-84 (`uploadCertificatePdf` ainda retorna `publicUrl`; `certificatePublicUrl` = `/object/public/certificates/{path}`) · src/lib/certificates/storage.ts:134-160 (`extractCertificatePath` normaliza PATH/URL pública legada/signed) · prisma/schema.prisma (Certificate: `studentName` + `studentCpf` snapshot embutidos no PDF)
- **Evidência:** Desde a última auditoria o read path foi consolidado: `generate-pdf.ts:181` grava `pdfUrl: upload.path` (PATH puro `"{tenant}/{certId}.pdf"`), **não mais** a URL pública. Os consumidores derivam o objeto com `extractCertificatePath` e servem via signed URL de curta duração / stream autenticado: `validar/[code]/page.tsx:283-290` (signed 300s, "Nunca expomos cert.pdfUrl"), `api/aluno/conta/route.ts:107`, `freshness.ts:82-97`. `certificatePublicUrl` continua **exportado** (storage.ts:82, index.ts:18) mas grep confirma que **nenhum read path o usa para servir** (só o retorno inócuo de `uploadCertificatePdf`). Resta: (a) o repo não prova que o bucket `certificates` é **privado** no Supabase; (b) linhas antigas de `Certificate.pdfUrl` ainda podem conter `/object/public/certificates/...` (o read normaliza on-the-fly, mas se o bucket for público a URL legada baixa o PDF com CPF sem auth). Memória do projeto ainda lista "R1 (CPF em bucket público) aberto".
- **Impacto:** Se o bucket `certificates` estiver **público** em produção, qualquer URL pública legada (compartilhada por e-mail/UI) baixa PDF com **CPF + nome completo** sem autenticação — vazamento de PII, LGPD art. 6/46; referência §7 classifica bucket público com PII como P0. Com o bucket privado, o risco é neutralizado (o código já serve via signed/stream).
- **Correção:**
  1. **(Infra/console — corretor PARA e descreve)** `select id, public from storage.buckets where id='certificates';` deve retornar `public=false`. Se `true`, tornar privado.
  2. Opcional (limpeza): `uploadCertificatePdf` parar de retornar `publicUrl` e `certificatePublicUrl` ser removido/depreciado, para eliminar qualquer caminho futuro de regressão.
  3. Backfill idempotente: `UPDATE certificates SET pdf_url = <path extraído> WHERE pdf_url LIKE '%/object/public/certificates/%';` (usando a mesma lógica de `extractCertificatePath`) para nenhuma linha guardar mais URL pública.
- **Verificação:** `GET` direto numa URL `/object/public/certificates/...` de um cert existente → 400/403 (bucket privado). `select count(*) from certificates where pdf_url like '%/object/public/%';` = 0. Aluno A não baixa PDF de B (403; `admin-scope.test.ts`).

### [DB-003] Sem RLS no banco — isolamento multi-tenant 100% em código (risco estrutural; agrava no cutover p/ Postgres self-hosted)
- **Severidade:** P1
- **Status:** Aberto
- **Local:** prisma/schema.prisma (44 models, nenhum com policy de tenant) · única RLS: prisma/migrations/20260430_notification_preferences/migration.sql (`ENABLE ROW LEVEL SECURITY` + policy `deny_anon` inócua) · src/lib/prisma.ts:15-21 (Pool `pg` conectando com a role do `DATABASE_URL`)
- **Evidência:** Varredura das 81 migrations: só `notification_preferences` tem `ENABLE ROW LEVEL SECURITY`, e a policy só nega o role `anon`. As demais 43 tabelas — `students` (CPF/RG cifrado), `payments`, `enrollments`, `tenant_payments`, `coupons`, `course_packages`, `email_logs` (e-mail plaintext), `webhook_logs` (payloads com PII), `referral_*`, `certificates` (CPF snapshot) — **não têm RLS**. O app conecta via `PrismaPg`/`pg` com a role do `DATABASE_URL` (owner), que **bypassa RLS** de qualquer forma. A defesa é 100% `where: { tenantId }` disciplinado em 309 route handlers.
- **Impacto:** Qualquer rota/action que esqueça o filtro `tenantId` vaza dados entre revendas — sem rede de segurança no banco. O BI hub novo aumenta a superfície (dezenas de agregações cross-tenant que dependem de o `segment`/`tenantId` estar correto). **⚠️MIGRAÇÃO:** ao sair do Supabase, somem `anon`/`authenticated`/`service_role`; "isolamento em código" exige cobertura de teste de isolamento por tenant antes do cutover.
- **Correção:** Decisão arquitetural (não mecânica): (1) habilitar RLS nas tabelas com coluna de tenant + rodar o app com role NÃO-owner e `SET app.current_tenant`/`SET ROLE` por transação — defesa em profundidade real; (2) no mínimo, um **teste de isolamento de tenant** automatizado (domínio `testes`) que prove que toda listagem loja/painel/BI filtra por tenant, e um guard/lint que falhe se uma query tenant-scoped não tiver `tenantId`. Ação imediata: ADR documentando a decisão + o teste de isolamento. Mudança de role/credencial = infra → corretor PARA e descreve.
- **Verificação:** `select n.nspname, c.relname from pg_class c join pg_namespace n on n.oid=c.relnamespace where c.relkind='r' and n.nspname='public' and c.relrowsecurity=false;` lista as 43 tabelas sem RLS. Teste: popular tenants A e B, autenticar como dono de A e garantir que nenhuma rota/aba de BI retorna registro de B.

### [DB-004] Padrão `$transaction([...map])` de array dinâmico permanece em 3 rotas de reordenação — é o MESMO construto que o time removeu de bulk-edit por falhar em prod (adapter-pg + pooler)
- **Severidade:** P1
- **Status:** Aberto (needs prod-repro; ver contra-evidência)
- **Local:** src/app/api/admin/treinamentos/reorder/route.ts:36-42 (`prisma.$transaction(orderedIds.map((id,i) => prisma.trainingModule/Video.update(...)))`) · src/lib/home/api.ts:328-331 (`reorderSections`: `updates = ids.map(...); await prisma.$transaction(updates)`) · src/lib/home/api.ts:362-363 (`$transaction(sections.map(...))`, `normalizePositions`) — chamados por src/app/api/admin/home-sections/reorder/route.ts:16 e src/app/api/painel/home-sections/reorder/route.ts
- **Evidência:** O commit 019a253 ("fix(cursos): edição em massa grava com updates sequenciais") documenta, **confirmado em prod**: "`prisma.$transaction([...])` sobre `@prisma/adapter-pg` + pooler do Supabase lançava e derrubava TODO o lote → 'não salva'". O fix trocou `catalogo/bulk/route.ts:111` e `painel/cursos/bulk/route.ts:114` por updates sequenciais. Porém as **rotas de reordenação** usam o **idêntico** array dinâmico `.map(...) → $transaction(...)`: reordenar módulos/vídeos de treinamento e — mais crítico — reordenar as seções da **home da vitrine** (admin e painel). Contra-evidência: `fulfill.ts:193/282` usa `$transaction([Payment.create, Enrollment.update])` (2 elementos fixos) e comprovadamente funciona em prod (pagamentos são gravados). Ou seja, o gatilho pode ser array **dinâmico/grande** e não todo `$transaction([...])` — mas o padrão exato marcado como "não salva" está presente e user-facing.
- **Impacto:** Se o diagnóstico do 019a253 valer para arrays `.map` dinâmicos, **reordenar seções da home** (loja pública) e **reordenar treinamentos** falha silenciosamente em prod: o admin arrasta, a UI fecha como sucesso, o banco não persiste a nova ordem — exatamente o sintoma "não salva" já visto na edição em massa. Reorder da vitrine é feature de configuração da loja → rota quebrada (P1 pela rubrica).
- **Correção:** Aplicar o mesmo remédio do 019a253 nas 3 rotas: trocar `$transaction(array.map(update))` por updates **sequenciais** isolados (loop `for … await prisma.x.update`), reportando falhas parciais; **ou** por um único `$executeRaw` com `UPDATE … SET position = CASE id … END WHERE id IN (...)` (uma statement, sem batch). Para `reorderSections` manter a normalização subsequente. Como reordenar posições precisa ser atômico em relação a leituras concorrentes, preferir a variante `UPDATE … CASE` (uma query) para não perder atomicidade.
- **Verificação:** Reproduzir em staging/prod com pooler: reordenar seções da home e treinamentos, recarregar e confirmar persistência. Após o fix, teste E2E de reorder + asserção de `position` no banco. Portão Zero-Erro verde.

### [DB-005] ⚠️MIGRAÇÃO/POOLING — `.env.example` aponta `DATABASE_URL` e `DIRECT_URL` para a porta direta (5432) em vez do pooler de transação (6543); Pool `pg` por instância pode esgotar conexões

- **Correção:** (verificação manual) Confirmar no Vercel que `DATABASE_URL` de **runtime** usa o pooler (`...pooler.supabase.com:6543/postgres?pgbouncer=true&connection_limit=1`) e `DIRECT_URL` a 5432 (DDL). Atualizar `.env.example:16-17` para refletir 6543 no `DATABASE_URL` e 5432 no `DIRECT_URL`. Com pgBouncer transaction mode, desabilitar prepared statements no `pg`/PrismaPg. **⚠️MIGRAÇÃO VPS:** Supavisor→pgBouncer (transaction mode), revisar `max_connections`; recursos session-mode exigem cuidado.
- **Verificação:** `select count(*) from pg_stat_activity where usename = current_user;` sob carga não cresce linear com o tráfego. Connection string de runtime contém `:6543` e `pgbouncer=true`.

### [DB-007] Runner de migrations envolve cada arquivo inteiro em UMA transação — armadilha latente para `ALTER TYPE … ADD VALUE`+uso e `CREATE INDEX CONCURRENTLY` no mesmo arquivo
- **Severidade:** P3
- **Status:** Aberto
- **Local:** scripts/apply-pending-migrations.mjs:153-172 (`BEGIN` → `client.query(file.content)` [todos os statements] → `COMMIT`) · prisma/migrations/20260628_lms_webhook_receiver/migration.sql (`ALTER TYPE "WebhookSource" ADD VALUE 'LMS'` + `CREATE UNIQUE INDEX` no mesmo arquivo) · comentários em 20260620_fk_indexes/20260620_pmb_null_unique_indexes/20260624 explicando "SEM CONCURRENTLY porque o runner usa transação"
- **Evidência:** O runner executa `file.content` (todos os statements) em UM `client.query` dentro de UM `BEGIN/COMMIT` (linhas 158-166). Os autores já **contornam** isso deliberadamente evitando `CONCURRENTLY` (grep de "CONCURRENTLY" só acha comentários explicando a ausência). As migrations com `ADD VALUE` funcionam porque o valor novo **não é usado** no mesmo arquivo (PG 12+). O desenho é frágil: a próxima migration que **usar** um enum recém-adicionado no mesmo arquivo, ou precisar de `CONCURRENTLY`, falhará em prod ("unsafe use of new value" / "CREATE INDEX CONCURRENTLY cannot run inside a transaction block"), abortando o `npm run build` (o `apply-pending` roda dentro do build).
- **Impacto:** Risco latente de migration que passa em revisão e quebra o deploy inteiro. Também limita a estratégia de índices de DB-001 (não dá para usar `CONCURRENTLY` pelo runner → índice em tabela grande bloqueia escritas).
- **Correção:** (1) Documentar no cabeçalho do runner que migrations com `ADD VALUE`+uso ou `CONCURRENTLY` DEVEM ser arquivos separados. (2) Melhor: detectar `CONCURRENTLY`/`ADD VALUE` no `file.content` e rodar esses arquivos **sem** `BEGIN/COMMIT` (autocommit por statement), habilitando índices concorrentes. (3) Convenção: `ADD VALUE` sempre isolado, antes da migration que usa o valor.
- **Verificação:** Migration de exemplo com `CREATE INDEX CONCURRENTLY` aplica sem erro pelo runner ajustado; cabeçalho reflete o comportamento real.

### [DB-009] Colunas de auditoria denormalizada sem FK nem índice (não-crítico — por design forense)

- **Status:** Aberto

### [DB-010] Drift schema↔banco: 4 índices de FK existem no banco (migrations SQL antigas) mas NÃO estão declarados em `schema.prisma`
